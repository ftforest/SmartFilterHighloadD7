# Baseline замеры (стандартный умный фильтр на инфоблоках)

**Дата:** 2026-10-14
**Стек:** PHP 8.4.1, MySQL 8.4.4, OSPanel/Windows, Bitrix `catalog.smart.filter` + `catalog.section`
**Данные:** 50 100 товаров, 9 свойств, фасетный индекс пересчитан
**Генерация данных:** 4 172.8 сек (~70 мин), 12 эл/сек

## Сценарий A — без фильтра
- SQL-запросов: 110
- Время SQL: 1.133 сек
- PHP PAGE TOTAL: 1.565 сек
- PEAK MEMORY: 32 MB

## Сценарий B — 1 фильтр (BRAND=Apple)
- SQL-запросов: 113
- Время SQL: 2.4077 сек
- PHP PAGE TOTAL: 2.847 сек

## Сценарий C — 3 фильтра (Apple + Чёрный + Металл)
- SQL-запросов: 115
- Время SQL: 2.2699 сек
- PHP PAGE TOTAL: 2.696 сек

## Сценарий D — 5 фильтров (Apple + Чёрный + Металл + XL + Китай)
- SQL-запросов: 117
- Время SQL: 2.5065 сек
- PHP PAGE TOTAL: 2.936 сек

## Наблюдения
- (что заметил: например, "при 3 фильтрах время растёт линейно",
  "кэш выключен", "пагинация показывает 50100 элементов",
  "запросы с PROPERTY_* содержат монструозные EXISTS-подзапросы" и т.д.)
- Замеры делались дважды. Разброс между прогонами — до ±20%, что нормально
  для локальной машины без тюнинга MySQL (buffer pool InnoDB, Windows).
  В таблицу выше занесены вторые замеры (совпадают со скриншотами).


## Наблюдения
- Кэш выключен (CACHE_TYPE=N) — измеряем реальную нагрузку.
- Количество SQL-запросов почти не растёт при добавлении фильтров (110 → 117),
  но время SQL растёт в 2.85 раза. Значит, дело не в числе запросов,
  а в сложности отдельных запросов, которые генерирует CIBlockElement::GetList
  при фильтрации по свойствам (PROPERTY_*).
- Первый фильтр даёт самый большой скачок (+72%). Остальные прирастают меньше
  благодаря фасетному индексу.
- Даже 1 фильтр = 2.29 сек — недопустимо для продакшна. Целевой показатель
  после оптимизации — до 500 мс.
- Основной подозреваемый: подзапросы к b_iblock_element_property (500k+ строк)
  с множественными EXISTS.
- Пиковая память стабильна (32 МБ) — утечек нет, дело только в SQL.

## Наблюдения
- Синхронизация 350 620 строк выполнена за 7 секунд при 777 SQL-запросах вместо 350 620 — скорость выросла в 450 раз по количеству запросов и в 595 раз по сравнению с поштучной вставкой через D7 ::add()
