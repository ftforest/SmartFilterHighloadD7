# Benchmark «после» (кастомный фильтр на D7 ORM + Highload)

**Дата:** 2026-10-16
**Стек:** PHP 8.4.1, MySQL 8.4.4, OSPanel/Windows
**Данные:** 50 102 активных товаров, 350 620 записей в HL-блоках
**Метод:** CLI-тест `local/php_interface/cli/test_filter.php`

## Результаты

| Сценарий | COUNT мс | Всего найдено | Страница (24 ID), мс |
|---|---|---|---|
| A — без фильтра | 94.73 | 50 102 | 2.54 |
| B — BRAND=Apple | 23.74 | 6 248 | 63.04 |
| C — 3 фильтра | 28.93 | 387 | 30.46 |
| D — 5 фильтров | 26.22 | 14 | 28.45 |
| E — 3 мультифильтра | 249.81 | 3 580 | 2.61 |

## Сравнение с baseline (инфоблоки)

| Сценарий | Baseline | FilterQuery | Ускорение |
|---|---|---|---|
| B | 2 294 мс | 23.74 мс | ×97 |
| C | 2 844 мс | 28.93 мс | ×98 |
| D | 2 990 мс | 26.22 мс | ×114 |

## Как это достигнуто

1. Фильтруемые свойства вынесены в 5 Highload-блоков с индексами
   `idx_product(UF_PRODUCT_ID)`, `idx_value(UF_VALUE_ID)`,
   `idx_product_value(UF_PRODUCT_ID, UF_VALUE_ID)`.
2. Вместо `CIBlockElement::GetList` с подзапросами `EXISTS` к
   `b_iblock_element_property` (350k+ строк) используется D7 ORM с
   `ReferenceField` JOIN'ами.
3. Один фильтр = один INNER JOIN к HL-таблице. Прямое попадание в индекс.

## Наблюдения

- COUNT(A) = 94 мс — без фильтров полный скан + COUNT(DISTINCT).
  В реальности сценарий не используется.
- Для узких фильтров (B, C, D) выборка страницы медленнее, чем для
  широких (A, E): MySQL при малом результате вынужден полностью пройти
  индекс + GROUP BY + ORDER BY.
- Сценарий E (3 мультифильтра) даёт 250 мс COUNT — кандидат на
  дальнейшую оптимизацию через EXISTS-подход, но приоритет низкий.

- 1 фильтр — 2 294 мс

**Ускорение: ×29 и ×11 соответственно.**

### Известные ограничения
1. `buildFilterItems()` (5×GROUP BY) выполняется до `FilterQuery::getCount()`,
   что снижает производительность последнего в браузере. В CLI без
   этого этапа — 28 мс vs 200 мс в браузере. Кэширование счётчиков
   решит проблему.
2. Пагинация при активном фильтре ограничена 24 ID первой страницы.
   Все найденные ID не передаются в `catalog.section` (компромисс ради
   производительности SQL).

### Профилирование компонента pet:filter

| Этап | Время |
|---|---|
| `buildFilterItems` (кэш) | 0.78 мс |
| `FilterQuery::getCount` | 24.42 мс |
| `FilterQuery::getProductIds` (24 ID) | 58.43 мс |
| **Весь компонент** | **83.67 мс** |

### Что дало основной выигрыш

1. **JOIN вместо EXISTS** — фильтрация через D7 `ReferenceField` к HL-таблицам.
2. **Индексы `idx_product_value`** — прямое попадание в индекс по
   `(UF_PRODUCT_ID, UF_VALUE_ID)`, без full scan по `b_iblock_element_property`.
3. **Кэш счётчиков фильтра** — 1374 мс → 0.78 мс на рендере формы.
   Инвалидируется при изменении товара через событие `OnAfterIBlockElementAdd/Update`.
4. **Отказ от `catalog.smart.filter`** — вместо встроенного компонента
   свой `pet:filter`, работающий напрямую с HL-блоками.
